# Internship Data Analytics Projects.

**Two practical analytics projects, taken from raw datasets to business-focused reporting.**

This repository brings together the two projects I worked on during my Data Analytics internship. My aim is to follow a complete and understandable analytics process: understand the business question, inspect the source data, prepare it carefully, validate the calculations, analyse the results and present useful findings through dashboards.

| **02 — Olist Brazilian E-Commerce** | Understand marketplace orders, customer behaviour, revenue and delivery experience | Python, Pandas, MySQL, Power BI | Order summary workbook, Order 360, Customer 360, RFM analysis and e-commerce dashboard |

## 1. Project 01 — IBM HR Analytics: Employee Attrition Analysis

Employee attrition can affect workforce continuity, recruitment effort and team planning. In this project, I explore employee-level HR data to understand where attrition is higher and which employee or workplace characteristics are associated with employees leaving.

### Business questions

- What is the overall employee attrition rate?
- Which departments and job roles have higher attrition rates?
- How does attrition vary across age groups, tenure, gender, marital status and education fields?
- How does attrition compare between employees who work overtime and those who do not?
- How are monthly income, job satisfaction and work-life balance associated with attrition?
- Which patterns could HR investigate further?

### Dataset

[IBM HR Analytics Employee Attrition & Performance — Kaggle](https://www.kaggle.com/datasets/pavansubhasht/ibm-hr-analytics-attrition-dataset)

Place `WA_Fn-UseC_-HR-Employee-Attrition.csv` in:

```text
project-01-ibm-hr-analytics/data/raw/
```

### Run the workflow

From the repository root:

```bash
python project-01-ibm-hr-analytics/python/profile_data.py
python project-01-ibm-hr-analytics/python/clean_data.py
python project-01-ibm-hr-analytics/python/analysis.py
```

The scripts create a data profile, a cleaned employee dataset, a KPI summary and grouped attrition reports. The SQL queries and Power BI report plan are documented in the project folder.

### Main KPI

**Attrition rate** = employees with `Attrition = Yes` divided by all employees in the selected population. Always show the numerator and denominator. A high percentage in a small job-role group should be interpreted with its employee count.

## 2. Project 02 — Olist Brazilian E-Commerce: Customer 360

Olist's marketplace data is split across multiple related files. Orders, customers, items, payments, products, sellers and reviews each describe a different part of the shopping experience. This project combines these sources carefully so that customer, order, revenue and delivery behaviour can be analysed consistently.

### Business questions

- How do order volumes and item revenue change over time?
- Which product categories and customer states contribute most to item revenue?
- What are the common order statuses and payment methods?
- How long do orders take to reach customers, and how often are they late?
- How many customers place more than one order?
- What do Recency, Frequency and Monetary (RFM) measures tell us about customer groups?
- How do review scores vary with delivery experience?

### Dataset

[Brazilian E-Commerce Public Dataset by Olist — Kaggle](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce)

Extract the CSV files into:

```text
project-02-olist-customer-360/data/raw/
```

Expected files:

```text
olist_orders_dataset.csv
olist_customers_dataset.csv
olist_order_items_dataset.csv
olist_order_payments_dataset.csv
olist_order_reviews_dataset.csv
olist_products_dataset.csv
olist_sellers_dataset.csv
olist_geolocation_dataset.csv
product_category_name_translation.csv
```

### Run the workflow

From the repository root:

```bash
python project-02-olist-customer-360/python/profile_data.py
python project-02-olist-customer-360/python/prepare_orders.py
python project-02-olist-customer-360/python/build_customer_360.py
```

Optional synthetic attribution demonstration:

```bash
python project-02-olist-customer-360/python/create_synthetic_marketing.py
```

The Olist workflow creates:

- a source-table and column profile;
- an Excel workbook with **Order Summary**, **Dataset Overview**, **Column Dictionary** and **Data Quality** sheets;
- a prepared order table with purchase and delivery metrics;
- an order-level analytical table combining customer, item, payment and review summaries;
- a customer-level table with RFM fields and segment labels.

### Important modelling decisions

- `order_id` identifies an order.
- `customer_id` links an order to its customer record.
- `customer_unique_id` is the more appropriate key for repeat-customer analysis.
- An order can have multiple item rows and multiple payment rows. Aggregate each child table to one row per order before joining, otherwise totals can be multiplied by join fan-out.
- Keep item revenue (`price`) and freight (`freight_value`) as separate measures.
- Historical customer revenue is not predictive Customer Lifetime Value (CLV).

### Attribution limitation

The standard Olist files do not include real marketing touchpoints or spend. Real first-touch, last-touch, linear and time-decay attribution, ROAS and CPA require valid session/touchpoint, conversion and campaign-spend data. The optional synthetic file is clearly marked as simulated and should only be used to demonstrate the calculations.

## 4. MySQL and Power BI workflow

1. Create a database in MySQL Workbench, such as `internship_analytics`.
2. Import the source CSVs into staging tables. Keep table and column names aligned with the SQL scripts, or update the scripts to match your import.
3. Run the SQL queries and check row counts, key uniqueness, join match rates and aggregate totals.
4. Connect Power BI to validated MySQL tables or the processed CSV outputs.
5. Follow the dashboard specifications in each project's `powerbi/` folder.
6. Reconcile the important Power BI measures against Python and SQL before presenting the results.

Do not save database passwords, API keys or other credentials in this repository.

## 5. Quality checks and testing

Run from the repository root:

```bash
pytest -q
```

The included tests check a few calculation and data-grain assumptions. They are starter tests, not proof that every row in your downloaded datasets has been validated. Record actual row counts, reconciliation checks, test output and any performance measurements in your final submission.

Before publishing a dashboard, check:

- primary-key uniqueness at the intended table grain;
- missing values and unexpected categories;
- unmatched join keys;
- revenue and order totals before and after joins;
- metric denominators and filter behaviour;
- documented assumptions, exclusions and known limitations.
